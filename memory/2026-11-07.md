## 07:30–08:10 — Fleet-wide fix for MiniMax 429s on cron jobs

### Trigger
- `BBC News Morning Drill` (88810bfe, gengar): 07:00 run **error** (206 s) —
  `⚠️ API rate limit reached` → auto-retry 07:03:58 **ok / delivered** (the drill did reach

- `群體智能架構研究` (b37129c0, roaringmoon): 08:00 run **error** (212 s) —
  same 429, delivery not-delivered; 2026-11-06 run had failed differently
  (`cron child-session handoff completed without a final assistant payload`).
- `push-llm-wiki` (e2ffd70d, mrmime) was `error (4x)` earlier in the week, now recovered.
- Provider log 06:55–07:10: 45× minimax-portal 200, 12× minimax (API key) 200,
  1× portal 429 + 2× API-key 429 → the API-key credential is a second, independent
  quota pool, so it is a real fallback.

### Root cause
MiniMax rate-limits the **portal** credential hard (whole 429 waves), and many jobs were
pinned to `minimax-portal/*` with **no** fallback to the API-key provider. Also
`agents.defaults.model.fallbacks` was `[]` fleet-wide, so every agent that inherits the
default primary had no fallback either.

### Fix applied (additive, reversible, no new credentials)
- `agents.defaults.model` = `{primary: minimax-portal/MiniMax-M3, fallbacks: [minimax/MiniMax-M3]}`
  (config backup `~/.openclaw/openclaw.json.bak-gengar-20261107`; hot-reloaded).
- Every agentTurn job whose primary was `minimax-portal/*` now also lists
  `minimax/MiniMax-M3` first in its `payload.fallbacks`
  (`minimax/MiniMax-M3,minimax-portal/MiniMax-M2.7,minimax-portal/MiniMax-M2.7-highspeed`).
  Verification: 29 agentTurn jobs scanned → **0** still portal-pinned without an API-key fallback.
- `agents.entries.gengar.model` stays `{primary: minimax/MiniMax-M3, fallbacks:[minimax-portal/MiniMax-M3]}`
  (API-key primary for gengar since Nov 1).
