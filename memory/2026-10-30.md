# 2026-10-30 Daily Log

## Gengar Cron Health Watchdog Auto-Disabled (10 consecutive "failures")

### Symptom
- Automation `29c2d630-7576-4da3-baae-5245177e5bcf` ("Gengar Cron Health Watchdog",
  cron `0 */2 * * *` Asia/Taipei, command payload) was auto-disabled at
  2026-10-30 00:04 with `autoDisabled.reason: consecutive-failures`,
  `consecutiveErrors: 10`.
- Every failing run looked identical: `error` / `command exited with code 1`,
  while stdout carried the alert text and `deliveryStatus: delivered`.
- Failing window: 2026-10-29 06:04 → 2026-10-30 00:04 (10 runs, every 2 h).

### Root Cause — two stacked bugs
1. **Self-destructing watchdog.** `scripts/check_gengar_crons.sh` exited `1`
   whenever it detected a problem. Per OpenClaw docs, a non-zero exit from a
   command payload records the run as `error` → consecutive-error counter →
   auto-disable after 10 failures. The watchdog killed itself with every alert.
2. **False-positive alert.** The script flagged `delivery == "not-delivered"` as a
   failure. The English reminder's normal pattern is: agent posts with the
   `message` tool and returns no final text → OpenClaw records
   `deliveryStatus: not-delivered` + `deliverySuppressionReason: "silent"` +
   `messageToolSentTo` — the message IS in the channel. So the watchdog was
   screaming about a healthy job every 2 hours (which is also why it started
   failing at 06:04 on Oct 29 — right after the reminder's 05:00 run recorded
   the silent pattern).

### Fix Applied
- Rewrote `scripts/check_gengar_crons.sh`:
  - **always exits 0** (problems are reported in stdout; NO_REPLY when healthy);
  - delivery verdict now reads the newest run entry and treats
    `suppression == "silent"` + non-empty `messageToolSentTo` as **healthy**;
  - still flags: job disabled, `consecutiveErrors > 0`, `lastRunStatus == error`,
    and a genuine delivery failure (not-delivered without the benign pattern).
- `openclaw automations enable 29c2d630-7576-4da3-baae-5245177e5bcf` → enabled,
  `consecutiveErrors: 0`, `autoDisabled` cleared.
- Manual verification run (00:05:41): **status ok**, completion succeeded,
  no error, delivery suppressed as silent (script printed NO_REPLY — both jobs
  healthy). Next run 02:04 Taipei. <!-- project: github.com/zhanzhanwu70-design/linderopenclaw-gengar -->
- Verified the alert path locally with a copy of the script pointed at a bogus
  job id: prints the alert, exits 0. Docs confirm non-empty stdout is what gets
  announced, and exit 0 records the run `ok` — so a real alert will still reach
  Discord without incrementing the error streak. <!-- project: github.com/zhanzhanwu70-design/linderopenclaw-gengar -->
- Swept every command-payload automation for the same pattern: only two exist
  (Gengar watchdog + Rowlet `transcription-monitor.sh`, which only ever
  `exit 0`). No other watchdog is self-destructing.

### Lessons
- **Command-payload automations must never exit non-zero to signal an alert.**
  Exit code = run status, not a severity channel. Report through stdout and
  keep exit 0; use the literal `NO_REPLY` for silence. <!-- project: github.com/zhanzhanwu70-design/linderopenclaw-gengar -->
- **Benign delivery pattern to recognize:** `deliveryStatus: "not-delivered"` +
  `deliverySuppressionReason: "silent"` + `messageToolSentTo` present = the agent
  posted directly to the channel and returned no final text. Message delivered;
  do not treat as failure.
- `openclaw automations enable <id>` clears both the failure streak and
  `autoDisabled`; `openclaw automations get <id>` exposes `state.lastDiagnostics`,
  `state.autoDisabled.reason` and `state.consecutiveErrors` — check those, not
  just `enabled`.
- Read `openclaw automations runs --id <id> --limit N` for per-run
  `status` / `deliveryStatus` / `deliverySuppressionReason` / `messageToolSentTo`.
