## English Reminder Cron Failed 2x (05:00 / 05:01 Taipei) — Host Uplink Outage, Not Provider

### Symptom
- Automation `ac9e7ada-134e-4b83-8161-6ec18ca312b9` ("You are an English coach…",
  cron `0 21 * * *` UTC = 05:00 Taipei) reported `error (2x)`.
- Run 1 (05:00:00, 73s): `LLM request failed: network connection error.`
- Run 2 (auto-retry, 05:01:43, 166s): `LLM request failed: DNS lookup for the provider endpoint failed.`
- Previous 4 days: `ok` / delivered. So this was a new, external-to-the-job failure.

### Root Cause (confirmed from journalctl)
- `2026-10-29 05:01:08` — `systemd-networkd: wlp0s20f3: Lost carrier`, then
  `wpa_supplicant: CTRL-EVENT-DISCONNECTED … SSID='hinet-141' reason=2`.
- NetworkManager then looped `wlp0s20f3: config -> failed (reason 'ssid-not-found')`
  every ~25 s until it re-associated at **05:07:54** (outage ≈ 6m45s).
- During the outage the host had **no default route**: the only surviving link
  `enp43s0` ("Wired connection 1", 192.168.50.1/24) is a **LAN-only link with no
  gateway**, so it cannot carry internet traffic.
- Evidence of total outage: 872 × `network is unreachable` in tailscaled logs,
  Discord websocket `1006` errors, and `defaultRoute=` empty in tailscale's
  LinkChange diff at 05:07:54.
- Provider side was healthy: `getent ahostsv4 api.minimax.io` OK, `curl` to
  `https://api.minimax.io/anthropic/v1/messages` → HTTP 404 (expected for GET),
  DNS lookup 0.8 ms.

### Recovery Applied
- `openclaw automations run ac9e7ada-134e-4b83-8161-6ec18ca312b9 --wait` →
  **ok, 13078 ms**. Reminder posted to Discord channel `1484513576482902158`
  (message id `1565110085393318002`).
- Job state restored: `lastRunStatus: ok`, `consecutiveErrors: 0`, `lastError: null`.
- Next run unchanged: 2026-10-29 21:00 UTC (2026-10-30 05:00 Taipei).
- Delivery reads `not-delivered` + `deliverySuppressionReason: silent` because the
  agent posted via the `message` tool and returned no final text — the message
  really is in the channel; this is the known benign pattern (same as 2026-10-25).

### Lessons
- On this host, `DNS lookup … failed` in a cron run usually means **local uplink
  loss**, not a provider/API problem. Check first:
  `journalctl --since "<window>" | grep -E 'Lost carrier|ssid-not-found|network is unreachable'`.
- The wired NIC is a LAN (192.168.50.x) with **no internet gateway** → it is not a
  backup uplink. A Wi-Fi drop = total internet loss on this box.
- Wi-Fi `hinet-141` drops 1–3×/day (21 events Oct 22–29), several in the
  02:00–06:00 window — exactly when the 05:00 reminder fires.
- The failure-alert → manual re-run path is the working catch-up: alert fired,
  job re-ran ~7 min later and delivered. No new cron job needed. <!-- project: github.com/zhanzhanwu70-design/linderopenclaw-gengar -->
- Diagnostic one-liners worth reusing:
  `openclaw automations get <id>` (state.lastDiagnostics / lastError),
  `openclaw automations runs --id <id> --limit 5` (per-run status + delivery),
  `openclaw automations run <id> --wait` (manual re-run, resets error streak). <!-- project: github.com/zhanzhanwu70-design/linderopenclaw-gengar -->
